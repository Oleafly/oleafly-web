# TeX 컴파일을 위한 프롬프트 모델

LaTeX용 채팅 모델에 문의하면 일반적으로 문서에서는 올바르게 보이지만 컴파일되지 않는 코드를 얻게 됩니다. 모델은 사용자가 어떤 클래스를 사용하는지, 어떤 패키지를 로드하는지, 어떤 매크로를 정의했는지 알지 못하므로 사용자의 것이 아닌 일부 일반 문서에 대해 응답합니다. 그런 다음 붙여넣는 순간 패키지가 누락되거나 정의가 충돌하여 출력이 종료됩니다. 대부분의 경우 세 가지 프롬프트 습관과 한 가지 엄격한 규칙, 즉 신뢰하기 전에 컴파일하면 피할 수 있습니다.

## 서문 보내기

귀하의 서문은 모델에 부족한 맥락입니다. 그것을 붙여넣거나 적어도 `\documentclass` 줄과 `\usepackage` 목록을 붙여넣고 "이 프리앰블 아래에서 컴파일되는 조각"을 요청하세요. 이 습관은 가장 일반적인 실패를 차단합니다. 대답은 `tikz`, `siunitx` 또는 로드한 적이 없는 다른 패키지에 자동으로 의존합니다. 또한 설정이 실제로 제공하는 명령을 향해 모델을 조정합니다. 프로젝트에서 매크로를 정의하는 경우 [모델에 기호 테이블 제공](/learn/ai-follow-notation/)에서 설명한 이유 때문에 해당 매크로도 포함하세요.

## 대답이 무엇에 달려 있는지 물어보세요

다음과 같은 고정 요청을 추가하세요. "내가 로드하지 않은 패키지가 코드에 필요한 경우 답변 상단에 명시적으로 나열하세요." 이는 숨겨진 종속성을 눈에 보이는 체크리스트로 바꿔줍니다. 응답이 패키지 이름을 지정하면 세 번의 컴파일 후에 '정의되지 않은 제어 시퀀스' 오류로 종속성을 발견하는 대신 패키지를 추가할지 여부를 결정합니다. 해당 오류와 해당 진단은 [정의되지 않은 제어 시퀀스](/learn/undefine-control-sequence/)에서 다룹니다.

## 다시 작성하지 말고 차이점을 요청하세요.

기존 텍스트를 변경하려면 가장 작은 관련 스니펫을 붙여넣고 요청에 필요한 것만 변경하도록 모델에 요청하여 변경된 내용을 명시하세요. 전체 파일이 주어지면 모델은 자유롭게 다시 작성합니다. 즉, 손대지 않은 단락의 형식을 다시 지정하고, 서문 줄의 순서를 변경하고, 때때로 바닥에 무언가를 떨어뜨립니다. 실제 변화는 이탈 속에서 사라집니다. 최소한의 설명된 편집은 실제로 검토할 수 있는 편집입니다. Oleafly 내부에서 어시스턴트는 [Oleafly 내부 어시스턴트](/learn/oleafly-ai/)에 설명된 대로 한 줄씩 승인하는 빨간색/녹색 차이점으로 모든 편집 내용을 제안하여 이 모양을 적용합니다.

## 신뢰하기 전에 컴파일하세요

아무리 그럴듯해도 컴파일하지 않은 LaTeX를 절대로 배송하지 마세요. 제안 사항을 문서에 붙여넣고 컴파일한 후 첫 번째 오류가 있으면 읽어보세요. 문제가 되는 코드 조각과 함께 해당 오류 메시지를 모델에 다시 제공하면 일반적으로 작동하는 두 번째 시도가 생성됩니다. 모델 지원 변경 사항을 하나의 명령으로 롤백할 수 있도록 프로젝트를 Git에 유지하세요. 이 설정은 [GitHub에 논문 게시](/learn/sync-with-github/)에서 설명합니다. 모델이 제안합니다. 컴파일러가 처리합니다.
